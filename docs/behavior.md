# Monitoring and safety semantics

## Eligible threads

`thread/started` registers candidates. A candidate must have `ephemeral: false`, a previously unknown ID, no fork/parent identity, and `createdAt` at least the next whole Unix second after monitor startup. This deliberately conservative timestamp policy can miss threads created in the startup second or with skewed server clocks. A startup `thread/list` baseline records known IDs. Old resumed threads are excluded even if their name is null. Ephemeral notifications are excluded before creation responses arrive, preventing helper recursion.

Only explicitly null current names are eligible. Empty strings count as names. Missing names after a metadata read cause deferral. The monitor rereads metadata and all available full-detail history for candidates. Empty/nontext-only user input defers. The first observed terminal turn (completed, failed or interrupted) with textual user input permits generation. A running turn defers collection. The utility does not attempt OCR, audio transcription or external-file loading.

In Codex 0.169.0, `thread/started` is broadcast to initialized clients of that server; live turn items and completion events are sent to thread subscribers. The utility never resumes, subscribes to, interrupts or sends turns to **source** threads. It polls only registered candidates for completion and current names. Reconnect repeats initialization, retains registered candidate IDs, captured snapshots and uncertain rename intents in memory, and resumes read-only polling. It does not adopt threads created entirely while disconnected. Restart establishes a fresh baseline; state is not persisted. No API scan turns historical unnamed threads into rename candidates. Other server processes and inaccessible remote history are outside the monitored scope.

One worker per source ID, bounded by `workers`, owns its snapshot and rename intent. Name-update notifications cancel active jobs. Subscriber-only or missed notifications are covered by the final metadata reread. A successful manual rename discards generated output. Codex 0.169.0 has no conditional name-set field: a residual race exists between the reread and `thread/name/set` if another client renames concurrently. Ambiguous writes retain their intended title and reread the name before any later action. A non-null result is accepted without replay; if it is still explicitly null a subsequent attempt can set the retained title. No mutation is blindly retried by the RPC client.

## Snapshot and truncation

History uses experimental `thread/turns/list`, `itemsView: full`, descending opaque-cursor pagination. This includes every item available from persisted App Server history, including unknown fields/types. Entire returned page objects are preserved as immutable JSON text. A snapshot records thread ID, retrieval start/end times, turn/item ID boundaries and SHA-256. Accessors return copies. Partial retrievals, non-full views, repeated cursors, duplicate turns and page-limit exhaustion do not produce snapshots.

Descending retrieval starts at the newest page observed and moves toward older history. Newly appended turns are not chased; a finite maximum page count additionally bounds retrieval. The API provides no server-side atomic snapshot token: concurrent edits, rollbacks or compaction can still affect older pages. Full means everything that this API exposes, not hidden raw provider content, inaccessible history or bytes of referenced files. `thread/items/list` is not additionally required because the selected full turn view includes the available items rather than summary/omitted views.

Each successful collection is frozen for every generation/context retry and reconnection. Later source activity cannot enter that job. Truncation changes only the input representation; snapshots are retained intact in memory. Complete history is used when it fits. Otherwise deterministic selection favors the first user request, subsequent/recent user messages and agent results over tools/logs, with marked item omissions and bounded prefixes for oversized items. Language evidence is sampled from original user messages before history selection, retaining beginning/end snippets; if the evidence itself is excessive it retains first/latest samples with an omission marker. The helper chooses dominant natural-language request language, latest substantive request on ambiguity, and is instructed to disregard code/logs/quotes. This is model-based language inference, not a guaranteed language classifier.

## Generation

Only `gpt-6-luna`, effort `low`, on the explicitly selected provider is accepted. `model/list` pagination checks model presence and advertised low effort, but supplies no context-window inference. A model-supported tiktoken mapping must exist; a guessed encoding is never used.

A small fresh ephemeral probe uses the same provider, model, effort, output schema and helper configuration. Successful runtime `thread/tokenUsage/updated` must contain positive integer `modelContextWindow` and input-token usage. Missing/invalid values defer. No discovered data is cached across jobs or connections, avoiding reuse across provider/config/auth/server changes. Source-thread context windows are never consulted.

The budget subtracts observed probe input (conservatively including probe text), schema token cost, configured output/reasoning reserve and safety margin from the discovered window. Automatic compaction threshold is explicitly placed above any usable context size; this is a compaction setting, not an assumed context capacity. The full formatted prompt is counted and recounted after truncation. Provider maximum-input constraints not exposed separately can still reject an attempt; a `contextWindowExceeded` response triggers bounded halving of the same snapshot's input representation in a fresh helper.

Helpers disable shell, web search, apps, multi-agent, code mode, JS REPL, automatic skill instructions and configured MCP servers, use no dynamic tools/environments, and request read-only sandbox with no approvals. Configuration policy may reject overrides, in which case jobs defer. Server-initiated tool/approval requests are rejected with an RPC error. Existing server capabilities and sandbox policy remain server-controlled; there is no universal protocol-level `tools: []` guarantee.

The listener is installed before start requests, so completion or usage arriving before acknowledgements is retained. Only successful terminal completion and a final agent answer are accepted. JSON schema requests one `title`, then Pydantic checks exact shape, nonempty trimmed single-line text and configured length. Helpers unsubscribe afterward; unfinished known turns are interrupted on failure/cancellation. If disconnection prevents cleanup, the server controls remaining helper lifetime. No helper is persisted intentionally and source operations remain reads plus the final name update.
